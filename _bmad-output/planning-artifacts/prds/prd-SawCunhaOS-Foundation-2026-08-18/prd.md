## Visão

A release 1.2.0 do `SawCunhaOS-Foundation` corrige defeitos reais já identificados (classificação errada de erro de autorização, colisão/concorrência na idempotência) e aproveita a janela de correção — enquanto o versionamento ainda é SNAPSHOT e a base de consumidores é piloto/restrita — para sanar a dívida estrutural que os causou (módulo `utils` monolítico e acoplamento invertido entre `utils`/`exception`), evitando que esses mesmos defeitos se repitam por herança de design quando a lib for adotada mais amplamente.

**Princípio de design do F1** (do plano de origem): *idempotência em cache é fast-path, não garantia*. Onde a chave é natural (ex.: `login`, `tenant+cpf`), a barreira real contra duplicidade é a constraint `UNIQUE` no banco — o Redis evita trabalho repetido, mas quando falha aberto (FR-4), é o banco que segura a garantia. Esse princípio deve estar documentado no README do módulo `jdempotent`, para nenhum time confiar no Redis como barreira única.

## Métricas de Sucesso

- Zero ocorrências de erro de autorização mal classificado (403 relatado como 500) após o deploy.
- Zero colisão ou duplicidade de processamento de idempotência em produção **em operação normal** (Redis disponível). Sob degradação (fail-open, FR-4), duplicidade é um risco aceito e catalogado — a garantia nesse cenário passa a ser a constraint `UNIQUE` do banco, não a idempotência em cache (ver princípio de design do F1 acima).
- Redução mensurável do conjunto de dependências transitivas para consumidores que usam apenas utilitários simples do `utils` (ex.: quem só precisa de `DateUtils` não carrega mais JPA/Redis/Feign).
- Cobertura de regras ArchUnit validando que cada módulo novo só importa o que seu papel permite (ex.: `core` não importa Spring, `*-api` não importa nada além de `jakarta.validation-api`).

### Contra-métricas

- Nº de regressões novas introduzidas nos módulos `exception`/`jdempotent` durante a refatoração (o plano é explícito: mover, não redesenhar).

## Features & Requisitos Funcionais

### F1 — Confiabilidade de Idempotência

- **FR-1**: Detectar colisão de chave entre fontes independentes com payloads diferentes (mesma chave, hash de payload distinto) e responder `422 PAYLOAD_MISMATCH` em vez de compartilhar a resposta cacheada.
- **FR-2**: Tornar a aquisição do lock de idempotência atômica via novo contrato `tryAcquire(key, payloadHash, ttl) → Lease`, substituindo o fluxo não-atômico `contains → store → setResponse`. Chamada concorrente com a mesma chave responde `409 IN_PROGRESS` em vez de `null` silencioso. O TTL do lease é configurável por método (não fixo), para acomodar operações mais longas que o padrão; a métrica `idempotency.in_progress` deve ser monitorada para detectar lease expirando antes do método terminar (risco catalogado no plano de origem, probabilidade média).
- **FR-3**: Suportar header `Idempotency-Key` como fonte de chave via `@JdempotentResource(keySource=HEADER_THEN_FIELDS, headerName="Idempotency-Key", onMismatch=CONFLICT)`, com precedência header → campos anotados → hash. Não reutilizar `X-Request-ID` para esse fim. O aspecto não é exclusivo de HTTP (também se aplica a listeners de mensageria): o resolver de chave deve devolver `null` de forma limpa e nunca lançar exceção quando não há contexto web disponível.
- **FR-4**: Garantir fail-open quando o Redis está indisponível (nunca `FAIL_CLOSED`), com circuit breaker (Resilience4j, `optional=true`) detectando lentidão via `slow-call-duration-threshold` — valor não fixado pela lib nesta versão, ver OQ-3 — respeitando `spring.data.redis.timeout`.
- **FR-5**: Migrar hashing de MD5 para SHA-256 (via enum `CryptographyAlgorithm`) e a formatação hex de `Integer.toHexString` para `HexFormat.of().formatHex()`.
- **FR-6**: Resolver campos anotados para composição de chave percorrendo toda a hierarquia de classes (não apenas `getDeclaredFields()`).
- **FR-7**: Expor métricas de idempotência via interface própria `IdempotencyMetrics` (implementação no-op por padrão, Micrometer condicional), incluindo no mínimo `idempotency.acquired`, `.hit`, `.in_progress`, `.mismatch`, `.backend_error`, `.degraded` (gauge 0/1) e `.degraded.transitions` (counter). Alertar quando `idempotency.degraded` permanecer em 1 por mais de N minutos (N a definir por ambiente). Taxa de `.hit` próxima de zero num endpoint com retry ativo é o sinal de que o cliente está gerando a chave dentro do laço de retry (ver OQ-8).
- **FR-8**: Introduzir `IdempotencyKeyResolver` e `@JdempotentProperty` como seletor explícito de campos, com serialização canônica (`TreeMap`) na composição de chave; `@JdempotentId` deixa de compor a chave.
- **FR-25**: Corrigir a inicialização com `RedisConnectionFactory` do Spring Boot em vez de montar `RedisSentinelConfiguration` própria e hardcoded — hoje isso causa NPE (`getSentinel()` nulo) em qualquer aplicação consumidora com Redis standalone ou cluster, não Sentinel.
- **FR-26**: Tornar a política de falha por exceção de negócio declarável por método — `RELEASE` (remove a chave, permite retry; comportamento atual, mantido como default) ou `KEEP_FAILED` (grava o erro como resultado, evita que um retry duplique um efeito colateral já ocorrido).
- **FR-27**: Posicionar o `@Order` do aspecto de idempotência fora do escopo do `@Transactional`, para que um rollback de transação não deixe a chave órfã no Redis.
- **FR-28**: Tornar obrigatório e configurável via propriedade Spring o namespace de prefixo de chave — hoje lido de `System.getenv(APP_NAME)`, fora do modelo de configuração do Spring e silenciosamente vazio quando ausente. Necessário porque a instância de Redis pode ser compartilhada entre aplicações.
- **FR-29**: Registrar `IdempotentAspect` com `@ConditionalOnMissingBean` (evita bean duplicado quando há mais de um ponto de registro) e remover o uso de `ThreadLocal` para `MessageDigest` (contraproducente com virtual threads; NPE latente).
- **FR-30**: Migrar a configuração de `@Value` para `@ConfigurationProperties`, removendo propriedades mortas sem período de depreciação (liberdade da janela SNAPSHOT), e corrigir o `EnvironmentPostProcessor` do módulo — hoje declarado incorretamente em `AutoConfiguration.imports` e por isso nunca executa.
- **FR-31**: Respeitar o TTL configurado em todos os construtores do `InMemoryIdempotentRepository` (hoje ignorado em 4 dos 7 construtores) e corrigir `equals`/`hashCode` do `IdempotentRequestWrapper` (hoje não-reflexivo e não-simétrico).
- **FR-32**: Adicionar allowlist de tipos permitidos no `PolymorphicRedisSerializer` antes do `Class.forName` sobre valor vindo do Redis — achado de segurança (desserialização de tipo arbitrário sem validação).
- **FR-33**: Substituir construtores telescópicos por builder no módulo `jdempotent`; documentar no README do módulo o princípio "cache é fast-path, não garantia" e a obrigatoriedade da constraint `UNIQUE` no banco para chaves naturais (ver Visão e NFR-6).

### F2 — Correção e Simplificação do Tratamento de Erros

- **FR-9**: Corrigir o handler de acesso negado para capturar `org.springframework.security.access.AccessDeniedException` (não `java.nio.file.AccessDeniedException`), restaurando o `403` correto em falha de autorização. Manter os dois handlers lado a lado — o existente para `AuthorizationDeniedException` (caminho novo do Spring Security 6) e o corrigido para `AccessDeniedException` (caminho antigo) — não é uma substituição de um pelo outro.
- **FR-10**: Corrigir o handler de validação para não lançar `IndexOutOfBoundsException` (`getBeanResults().get(0)`) quando a violação ocorre em parâmetro simples (ex.: `@RequestParam @Min(1) int page`) em vez de bean — hoje isso mascara um `400` como `500`. Iterar sobre `getBeanResults()` e também `getValueResults()`.
- **FR-11**: Extinguir `scos-foundation-exception`, dividindo em contrato de domínio no `core` (`ScosException`, `ExceptionCode`, `ScosExceptionCode`, `LocaleService`, `ScosNoContentException`, `ScosNoRollbackException`, `ScosSecurityException`, `MethodNotImplementedException`) e tradução HTTP em `scos-foundation-web` (`ExceptionsHandler`, `ScosProblemDetails`, `ScosFieldError`, `ExceptionUtils`). Repontar o módulo `audit` para consumir `ScosException` do `core` (hoje depende de `exception`, que traz `spring-web`/`spring-security-core` sem necessidade). Nota: `LocaleService` hoje é uma interface pura (`java.util` apenas, sem import de Spring, sem implementação de produção) — cabe no `core` sem violar a regra "core não importa Spring" (FR-19). Qualquer implementação futura que precise de `MessageSource`/`LocaleContextHolder` do Spring deve viver fora do `core` (ex.: `spring` ou `web`).
- **FR-12**: Registrar `ExceptionsHandler` via `AutoConfiguration.imports`, com `@ConditionalOnProperty(scos.web.error-handler.enabled, matchIfMissing=true)` e `@Order(Ordered.LOWEST_PRECEDENCE)`.
- **FR-13**: Sobrescrever `handleExceptionInternal` para unificar o formato de erro em todos os casos, incluindo 404 / rota inexistente.
- **FR-14**: Substituir o parsing por regex em `resolveTitle` por navegação de causa (`InvalidFormatException`/`MismatchedInputException.getPath()`), compatível com Jackson 3.
- **FR-15**: Retornar `501` para `MethodNotImplementedException` (hoje `500` genérico).
- **FR-16**: Padronizar log por faixa de status — `4xx` em `WARN` sem stack trace, `5xx` em `ERROR` com stack trace, `ScosNoContentException` (204) em `DEBUG` — e padronizar uso de `@Slf4j` (remover Log4j2 direto). O handler genérico (fallback sem tipo específico) é o único que carrega `ERROR` incondicionalmente, independente da faixa de status.
- **FR-17**: Consolidar a constante `MDC_REQUEST_ID`, hoje duplicada entre `ScosProblemDetails` e `LoggingInitialFilter`, no módulo `core`.
- **FR-34**: Corrigir `resolveTitle`, que hoje usa `try/catch` como controle de fluxo para testar a existência de uma chave no bundle de mensagens — mascara falhas reais do `LocaleService` e devolve um literal em inglês ("Business Error") numa API localizada. `LocaleService` ganha `getMessageOrDefault(code, default)`, com o default vindo de `ExceptionCode.getTitle()` (já existe e já tem valor).

### F3 — Decomposição Modular do `utils`

**Decisões do PM nesta consolidação** (D1–D3 não vêm literalmente dos planos de origem — são julgamento tomado durante esta calibração; alternativa rejeitada citada em cada uma):
- **D1** (`@Cacheable`): `web` aceita dependência formal de `cache`. Rejeitado: remover `@Cacheable` das meta-anotações — descartado porque elas servem para uso com Spring controller e habilitar cache quando presente, não faz sentido separar.
- **D2** (value objects): `Cpf`/`Cnpj`/`Email`/`TaxIdentifier` ficam em `validation`. Rejeitado: mover para `jpa` — descartado para manter os value objects junto da validação que os acompanha, aceitando `jakarta.persistence-api` como `provided`.
- **D3** (Feign): módulo próprio dedicado. Rejeitado: `optional` dentro de `web` (inclinação original do plano) — descartado por isolamento total de dependência, mesmo para só 2 classes.

- **FR-18**: Dividir `scos-foundation-utils` nos módulos `core`, `spring`, `web`, `cache`, `jpa`, `validation`, `audit-api`, `jdempotent-api`, `validation-api` e `feign` (decisão D3). `web` mantém `@Cacheable` embutido em `ScosRequestGET/POST/PUT/DELETE` e aceita a dependência formal de `cache` (decisão D1). Value objects (`Cpf`, `Cnpj`, `Email`, `TaxIdentifier`) ficam em `validation`, que passa a ter `jakarta.persistence-api` como `provided` (decisão D2). Divisão por fase do Sequenciamento: passo 3 cria `audit-api`/`jdempotent-api`/`validation-api`; passo 4 extrai `core`; passo 6 extrai `spring`, `validation`, `cache`, `jpa`, `web` e `feign`, nessa ordem (do menos para o mais acoplado).
- **FR-19**: Impor por regra estrutural: `core` não importa `org.springframework`, `jakarta.persistence` nem `jakarta.servlet`; `spring` não importa `jakarta.servlet`/`jakarta.persistence`/`spring.data`; módulos `*-api` contêm apenas `@interface`/`enum`, sem dependência além de `jakarta.validation-api`; nenhum módulo depende de `web` exceto aplicações; sem ciclos entre módulos; proibida a criação de pacote chamado `utils.utils` ou equivalente (repete o antipadrão que originou a decomposição).
- **FR-20**: Impor as regras do FR-19 via testes ArchUnit no perfil `analyze`, promovido de 4/5 poms para `pluginManagement` do POM pai (cobertura em 100% dos módulos). Cada regra entra no mesmo commit que cria o módulo que ela protege — a regra "`core` não importa Spring" nasce junto com a extração do `core` (Sequenciamento passo 4), a regra dos `*-api` nasce junto com a criação deles (passo 3) — em vez de todas as regras serem adicionadas de uma vez só ao final da decomposição, o que deixaria os módulos mais sensíveis ao acoplamento invertido (justamente `core` e `*-api`) sem proteção durante sua própria extração.
- **FR-21**: Migrar serialização JSON de Gson para Jackson em toda a base — remover `GsonUtils` e os 3 adapters de `java.time`; migrar `JsonMasker` (módulo `privacy`) e os 4 pontos de uso em `audit` (`ScosAuditHashService`, `ScosAuditServiceBean`, `ScosAuditBatchConsumer`, `ScosAuditDlqJob`) — preservando a política de nulos (`@JsonInclude`, documentada no README do `audit`, já que Gson omite nulos e Jackson inclui) e a característica O(n) do caminho quente do `JsonMasker` (critério de pronto: revisão manual no code review confirmando que a lógica de mascaramento permanece um único loop O(n); sem benchmark automatizado nesta versão — aceito conscientemente).
- **FR-22**: Remover dependências mortas (`bouncycastle`, `snakeyaml`, `mapstruct` — 0 usos), substituir `guava` (1 uso) por `commons-lang3`, avaliar substituição de `commons-io` por `java.nio`, e avaliar a necessidade real de `spring-cloud-starter` (3 usos).
- **FR-23**: Congelar, na Fase 0, o inventário de destino módulo-a-módulo das 71 classes atuais — nenhuma classe pode ficar sem destino.
- **FR-24**: Emitir log `INFO` na inicialização de cada **módulo de implementação** (ex.: `jdempotent`, `audit`, `validation` — não o `*-api` correspondente, que por FR-19 não pode ter lógica nem dependência de runtime) contando quantas classes anotadas foram encontradas na aplicação consumidora (mitiga uso de um módulo `-api` sem a implementação correspondente no classpath, que hoje compilaria mas não executaria nada silenciosamente). Cada README de módulo `-api` abre com a frase "este artefato não executa nada; a implementação é `scos-foundation-<x>`".

## Sequenciamento e Fases

Os 3 planos tocam os mesmos arquivos e têm ordem de execução obrigatória — corrigir comportamento com o módulo parado, mover depois, para manter o diff de cada commit separável entre "correção" e "renomeação". Ordem definida na origem (`plano-ajuste-exception.md`, seção 9):

| # | Plano | Fase(s) | O que acontece | Por quê |
|---|---|---|---|---|
| 1 | F3 (`utils`) | Fase 0, 1 e 1.5 | Rede de proteção, limpeza de dependências mortas, migração Gson→Jackson (FR-21 a FR-23) | Limpar terreno antes de qualquer movimentação de classe |
| 2 | F2 (`exception`) | Fase 0 a 2 | Testes de regressão + correções internas do bug 403/500, do `IndexOutOfBoundsException` e do log (FR-9, FR-10, FR-12 a FR-17), com o módulo ainda no lugar | Diff limpo — corrigir sem misturar com mudança de pacote |
| 3 | F3 (`utils`) | Fase 2 | Criar os módulos `*-api` e mover as anotações `@Jdempotent*`/`@Auditable`/`*-api` (parte de FR-18) | Menor risco, maior ganho isolado — quebra o acoplamento reverso |
| 4 | F3 (`utils`) | Fase 3 | Extrair o `core` (parte de FR-18) | Tudo depende dele, sai primeiro |
| 5 | F2 (`exception`) | Fase 3 | Mover a hierarquia de exceções para o `core` que acabou de ser criado, repontar `audit` (FR-11, FR-34) | Só é possível depois que o `core` existe |
| 6 | F3 (`utils`) | Fase 4 e 5 | Extrair módulos folha `spring → validation → cache → jpa → web → feign` (recebendo `ExceptionsHandler`) e remover o `utils` do reactor (resto de FR-18 a FR-20, FR-22, FR-24) | Do menos para o mais acoplado |
| 7 | F1 (`jdempotent`) | Todas as fases | Contrato `tryAcquire`/`Lease`, header `Idempotency-Key`, fail-open, correções de configuração e segurança (FR-1 a FR-8, FR-25 a FR-33) | Dependência técnica mínima real: só a Fase 2 do F3 (passo 3), que devolve as anotações `@Jdempotent*` ao módulo `jdempotent-api`. A posição no fim da tabela é escolha deliberadamente conservadora do plano de origem — evita rodar 3 refatorações tocando arquivos adjacentes ao mesmo tempo — não uma dependência estrutural do F1 no `core` ou nos módulos folha |

Fases internas do plano de origem do F1 (dentro do passo 7 acima), para referência de quem for cortar escopo (ver OQ-2): Fase 0 rede de proteção → Fase 1 correção de chaves (FR-5, FR-6, FR-29) → Fase 2 execução simultânea (FR-2, FR-25 a FR-28) → Fase 3 chave composta declarativa (FR-8) → Fase 4 header (FR-3) → Fase 5 endurecimento, em paralelo (FR-30 a FR-33).

Dependência externa a este PRD (fora dos 3 planos, não controlada aqui): a Fase 1.5 do F3 (migração Gson→Jackson) precisa que o hash-chain do módulo `audit` seja removido antes, pois a migração muda o hash calculado sobre o JSON serializado (ver OQ-4).

## Requisitos Não Funcionais

- **NFR-1 (ordem de execução)**: seguir a tabela de `## Sequenciamento e Fases` — nenhuma fase pode ser adiantada em relação à sua dependência ali listada.
- **NFR-2 (segurança de refatoração)**: build verde a cada commit/módulo extraído; cada extração de módulo em 2 commits separados (mover/renomear vs. ajustar comportamento) — nunca misturados na mesma revisão.
- **NFR-3 (cobertura de teste)**: `jacoco:check` com mínimo de 80% nas áreas tocadas pela Fase 0 do F1 (testes de concorrência, colisão de hex, duplo `IdempotentAspect`, indisponibilidade de Redis via Testcontainers).
- **NFR-4 (escopo de mudança)**: nenhuma alteração de comportamento além do declarado durante mover/renomear — risco explícito identificado nos planos de origem é a refatoração de decomposição "virar reescrita".
- **NFR-5 (TDD no F2)**: cada correção de bug do F2 (FR-9, FR-10, FR-34, e o contrato de formato de 404 do FR-13) exige um teste que reproduza o bug e falhe antes do fix — mesmo espírito da Fase 0 do F1 (NFR-3), aplicado ao F2.
- **NFR-6 (garantia de dados sob fail-open)**: todo método com chave de idempotência natural deve ter constraint `UNIQUE` no banco antes de habilitar o `jdempotent` — não é recomendação, é pré-requisito. Documentado no checklist de revisão de endpoints e no README do módulo (ver FR-33).
- **NFR-7 (piso de documentação, repo inteiro)**: todo módulo — novo ou existente, incluindo `audit` e `privacy`, que este PRD não toca funcionalmente — exige Javadoc em API pública (Checkstyle já existente, promovido a `pluginManagement` do POM pai, mesmo veículo do FR-20), comentário inline onde a lógica não é óbvia (cobrado em revisão, sem gate mecânico), diagrama de fluxo de uso em Mermaid inline no README, e README obrigatório por módulo. Decisão tomada na consolidação da arquitetura (spine de 2026-08-19), não vem dos planos de origem — **bloqueia o release da 1.2.0** (ver OQ-9).

## Comunicação e Migração

Sem processo formal de guia de migração ou aviso direto aos consumidores. Dupla justificativa: (1) decisão do usuário nesta calibração — versão ainda SNAPSHOT, base de consumo piloto/restrita; (2) o próprio plano de decomposição do `utils` já declara explicitamente que "compatibilidade com consumidores não é restrição neste ciclo", elegendo de propósito não manter agregador de transição nem depreciação. O CHANGELOG do repositório é a única superfície de comunicação — cada frente registra sua própria entrada no momento em que seus commits sobem (F2 registra as mudanças de status HTTP já na Fase 0-2 do Sequenciamento, não espera a Fase 5 do F3), em vez de um único changelog consolidado só ao final. Complementarmente, a Fase 5 do F3 entrega um README na raiz do `utils` com uma tabela "quero X → importe o módulo Y", mapeando capacidade a módulo de destino para quem for atualizar imports depois da decomposição.

## Riscos e Questões em Aberto

- **OQ-1 (mudança de status HTTP observável)**: rotas que hoje respondem `500` passam a responder `403` (FR-9), `400` (FR-10) ou `501` (FR-15). Risco aceito intencionalmente pelos planos de origem — consumidores que dependiam do comportamento antigo (mesmo incorreto) podem quebrar. *Dono*: responsável pelo F2. *Condição de revisão*: monitorar taxa de erro por status código nos primeiros dias após o deploy da 1.2.0.
- **OQ-2 (corte de escopo sob pressão de prazo)**: se o prazo apertar, a diretriz é cortar volume de trabalho, nunca quebrar contrato (nunca introduzir lock não-atômico ou fail-closed silencioso). Concretamente: as fases internas 3 a 5 do plano de origem do F1 (chave composta declarativa, header, endurecimento — FR-8, FR-3 e FR-30 a FR-33, ver tabela de `## Sequenciamento e Fases`) podem ser adiadas; Fases 0-2 (FR-1, FR-2, FR-5 a FR-7, FR-25 a FR-27, FR-29) já entregam um módulo correto e não são candidatas a corte. *Dono*: quem executa a implementação. *Condição de revisão*: revisitar se o esforço ultrapassar ~17 dias úteis (metade do teto estimado combinado, ajustado de 21-28 para 24-33 dias após a inclusão do NFR-7).
- **OQ-3 (dimensionamento de timeout/circuit breaker)**: nenhum valor de timeout ou `slow-call-duration-threshold` é fixado pela lib (FR-4) — fica como recomendação, a dimensionar por ambiente de consumo. *Dono*: time consumidor em cada ambiente. *Condição de revisão*: antes do primeiro deploy em ambiente com tráfego real.
- **OQ-4 (hash-chain do audit)**: a migração do serializer (FR-21) muda o hash calculado sobre o JSON serializado; cadeias de hash existentes no `audit` ficam inválidas se não forem removidas/reprocessadas antes da migração (dependência externa listada em `## Sequenciamento e Fases`). *Dono*: responsável pelo módulo `audit`. *Condição de revisão*: confirmar se existe alguma cadeia de hash-chain persistida em ambiente piloto antes de iniciar FR-21.
- **OQ-5 (renomeação mascarando mudança de comportamento)**: risco médio de que a reorganização de pacotes do F3 esconda, no diff, uma mudança de comportamento não intencional. Mitigação já coberta por NFR-2 (commits separados mover/renomear vs. ajuste); mantido como item de atenção na revisão de código.
- **OQ-6 (handleExceptionInternal muda o formato de erros nativos do Spring)**: FR-13 unifica o formato de erro inclusive para casos hoje tratados nativamente pela superclasse do Spring (404, método não suportado, media type inválido) — risco "Alta, é o objetivo" no plano de origem, mesmo nível do OQ-1, mas sobre o corpo da resposta em vez do status code. *Dono*: responsável pelo F2. *Condição de revisão*: mesma janela de monitoramento do OQ-1.
- **OQ-7 (regex do FR-14 pode já estar quebrado em Jackson 3)**: o regex que o FR-14 substitui pode já não casar com as mensagens do Jackson 3 antes mesmo da correção, falhando silenciosamente. Probabilidade média, mitigado pelo teste da Fase 0 do F2 (NFR-5). *Dono*: responsável pelo F2. *Condição de revisão*: confirmar via teste de Fase 0 antes de aplicar FR-14.
- **OQ-8 (riscos de alta probabilidade do F1)**: (a) cliente gerar a chave de idempotência dentro do laço de retry — mitigado por documentação + revisão da primeira integração + métrica `idempotency.hit` próxima de zero (FR-7); (b) fail-open lento (Redis fora somando até 5s por requisição) saturando o pool de threads antes de qualquer alerta disparar — mitigado por FR-4 (circuit breaker) e timeout de comando reduzido. *Dono*: responsável pelo F1. *Condição de revisão*: validar os dois cenários em teste de carga antes do primeiro deploy em produção.
- **OQ-9 (gate mecânico do NFR-7 não confirmado)**: o `maven-checkstyle-plugin` já está configurado em 4 dos 5 módulos, mas a execução com `goal=check`/`failOnViolation` não foi encontrada localmente nesta revisão — pode estar em `pluginManagement` do `scos-bom` (parent externo) ou pode não estar de fato amarrada. ## Glossário

- **fail-open / fail-closed**: comportamento do módulo `jdempotent` quando o Redis está indisponível. Fail-open (adotado, FR-4) deixa a requisição de negócio prosseguir sem a garantia de idempotência; fail-closed (não usado) bloquearia a requisição.
- **colisão de chave** (FR-1): duas requisições de negócio distintas geram, por acidente, a mesma chave de idempotência — problema de geração de chave.
- **colisão de hex** (NFR-3): teste de colisão criptográfica no hashing (payloads escolhidos para produzir o mesmo hash) — conceito de hash, distinto de colisão de chave de negócio.
- **lock de idempotência**: o registro que marca uma chave como "em processamento", adquirido atomicamente pelo `tryAcquire` (FR-2) para impedir execução concorrente duplicada.
