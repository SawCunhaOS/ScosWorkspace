- (note by user) Pedido inicial: uso do scos-map hoje é mais lento que grep puro; proposta é criar pequenos scripts Python que o agente chama, retornando saída estilo grep mas voltada à estrutura do scos-map
- (insight by user) Dor é custo de tokens, não latência: consultar via scos-map (ler JSON/facts inteiros) consome mais tokens de contexto do que um grep equivalente
- (decision by user) Stakes: Interno. Modo: Fast path. Chamador: só o agente (Claude Code) via Bash. Escopo: Tier 1 a 3 completo
- (idea by user) Ideia de mecanismo: chamar os scripts via subagent com modelo mais barato, que devolve os dados já tratados/curados ao agente principal — reduz alucinação e mantém a saída bruta fora do contexto principal
- (note) Levantamento: scos-map.py só tem scan/workspace/status hoje — não existe modo de consulta; agente lê JSON inteiro via Read. TSV já tem padrão awk barato no SKILL.md; o problema é só JSON minificado em uma linha (ex.: config.json do Flow usecase = 142KB numa linha, layout.json = 54KB)
- (note) Prior art equivalente: jq (filtro compacto sobre JSON), ast-grep/ripgrep (saída line-oriented), ctags (índice símbolo→local), Aider repo-map (resumo estrutural). Padrão 'subagent com modelo barato resume tool output' é a própria mecânica de fork/subagent do Claude Code, não um produto de mercado citável
- (decision) Decisão do PM (sem pergunta ao usuário): saída compacta deve sempre carregar um indicador mínimo de confiança/frescor (derivado de confianca/obsoleto), porque omitir isso reintroduziria a alucinação que o pedido quer evitar
- (decision) Decisão do PM: mecanismo de invocação via subagent+modelo barato entra como requisito de capacidade (scripts expõem CLI/saída estável e documentada para consumo por subagent); orquestração específica (qual modelo, como o subagent é disparado) vai para addendum.md, não é FR do script em si
